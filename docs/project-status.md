# GrowwLens Project Status and End-to-End Documentation

## 1. Executive summary

GrowwLens is an event-driven market-intelligence watchlist prototype built for the
“Code, by Groww” challenge. Its central product idea is:

> A watchlist that explains what changed, why it changed, how important the change
> is, and reliably notifies the user across devices.

The current repository contains a working full-stack demo with:

- React/Vite frontend styled as a Groww-inspired trading terminal.
- FastAPI/Python backend.
- PostgreSQL as the preferred database, with SQLite fallback for offline tests/dev.
- Redis Streams market event bus with an explicit local queue fallback.
- Simulated market ticks, with optional Groww SDK and IndianStockAPI integrations.
- Deterministic technical/change detection.
- Stateful, idempotent price alerts.
- In-app, WebSocket, and optional Resend email notifications.
- Watchlists, pinning, orders/holdings, news timelines, related stocks, and heatmaps.
- Automated backend tests for initialization, analytics, alert races, orders, and pinning.

This is a strong prototype/demo implementation. PostgreSQL and Redis Streams are
now the preferred local runtime architecture. SQLite and an in-process queue remain
explicit fallbacks for offline tests/development. Separate workers, authentication,
and a true external real-time feed are still future production work.

## 3. Product capabilities delivered

### Watchlists

- Multiple seeded watchlists, including default, defence/infrastructure, technology,
  Nifty-heavyweight, and international/market views.
- Create and delete watchlists.
- Add and remove symbols.
- Pin/unpin symbols atomically.
- Persist symbol, company, sector, position, added price, last-seen price,
  last-seen volume, and last-seen attention score.
- Live enrichment of each row with price, daily change, volume, EMA, pressure,
  anomaly state, sparkline, and attention metadata.

### “What changed”

The backend compares current market state to each watchlist item’s persisted
`last_seen_*` fields. The report can show:

- Price movement since the previous visit.
- Volume and volume-ratio changes.
- Attention-score changes.
- Meaningful changes generated by the change engine.
- A mark-seen action that updates the baseline.

### Market intelligence

The canonical `MarketEvent` includes symbol, timestamp, price, volume, interval
volume, OHLC values, previous close, daily change, source, and sequence number.

For each event the change engine calculates:

- EMA20 and EMA50.
- EMA20 bullish/bearish crossover.
- Interval volume ratio versus a proportional five-minute baseline.
- Volume anomaly when the ratio is at least `2.0x`.
- Signed-volume buy and sell pressure.
- Rolling volatility estimates.
- A 0–100 attention score.
- Human-readable meaningful changes for volume, technical, price, pressure, and
  catalyst conditions.

The score weights price movement, volume, technical state, volatility, and news.
It is deterministic and does not claim to predict prices.

### Alerts and notifications

Alerts support:

- Greater-than and less-than price conditions.
- Positive thresholds.
- `ARMED`, `TRIGGERED`, `COOLDOWN`, and re-arming behavior.
- A configurable 60-second cooldown.
- One canonical alert event per `(alert_id, market_event_id)`.
- One in-app notification and one queued email job per logical trigger.
- Concurrent race-condition demonstration through `/api/alerts/simulate-race`.

Connected clients receive alert messages through WebSockets. Email uses Resend
when `RESEND_API_KEY` is configured; otherwise delivery is recorded as simulated.

### Cross-device synchronization

The frontend connects with a user and device identity in the WebSocket query
string. Mutations such as watchlist edits, pin changes, and order execution can
be broadcast as `CROSS_DEVICE_MUTATION` messages. Alert fanout sends one logical
event to all active sockets for the user.

The UI models MacBook, iPhone, and iPad sessions and displays device status.

### Trading and portfolio demo

- Buy and sell modal flows.
- Order validation for action, positive quantity, and positive price.
- Order persistence in `orders`.
- Holdings persistence in `portfolio_holdings`.
- Rejection of sells larger than the held quantity.
- Cross-device order mutation broadcast.

These are demo/trading-simulation operations, not broker order execution unless
the future Groww order API is added.

### News, terminal, and discovery

- Stock terminal with candlestick history generated by the backend.
- Volume/order-book style panel.
- Stock-specific timeline connecting news, volume, pressure, price, and EMA events.
- News feed using IndianStockAPI when configured, otherwise an empty/provider-safe
  result.
- Related stocks based on sector and return correlation.
- Peer lookup through the IndianStockAPI integration with local fallback behavior.
- Sector market heatmap.

## 4. Technology stack actually used

### Frontend

- React 19.
- TypeScript 6.
- Vite 8.
- Tailwind CSS 4 with the Vite plugin.
- `lightweight-charts` 5 for charts.
- `lucide-react` for icons.
- `clsx` and `tailwind-merge` for class composition.
- `oxlint` for linting.

Main UI areas are in [`frontend/src/App.tsx`](../frontend/src/App.tsx):
header/index strip, watchlist table, What Changed banner, terminal, heatmap,
notification center, alert/order modals, race-condition demo, and news drawer.

### Backend

- Python.
- FastAPI.
- Pydantic models.
- Uvicorn runtime.
- PostgreSQL via `psycopg` with native row locks; SQLite retains WAL mode, foreign keys,
  busy timeout, and explicit transactions for offline fallback.
- `asyncio` for the market loop, WebSocket fanout, and email task.
- `httpx` for Resend and Groww-related HTTP calls.
- `growwapi` for optional Groww SDK access.

### Data and integrations

- Preferred durable database: PostgreSQL via `DATABASE_URL`; `backend/groww_lens.db`
  is the offline SQLite fallback.
- Schema: [`backend/app/db/schema.sql`](../backend/app/db/schema.sql).
- Optional Groww credentials: `GROWW_API_KEY`, `GROWW_API_SECRET`.
- Optional IndianStockAPI: `INDIAN_STOCK_API_KEY`,
  `INDIAN_STOCK_API_URL`.
- Optional Resend: `RESEND_API_KEY`, `RESEND_FROM_EMAIL`.
- Finnhub/Twelve Data settings exist, but they are not the active market-stream
  implementation in the current adapter.

## 5. Runtime architecture

```text
React/Vite browser
        │ REST + WebSocket
        ▼
FastAPI application
        │
        ├── PostgreSQL source of truth (SQLite/WAL fallback)
        ├── MarketProviderAdapter → Redis Streams (local queue fallback)
        │       ├── simulator ticks
        │       └── optional Groww synchronization
        ├── MeaningfulChangeEngine
        ├── AlertEngine
        ├── NotificationService
        ├── NewsTimelineService
        └── RelatedStockService
```

At startup, FastAPI initializes the database and starts the market adapter task.
Each market event is processed by the change engine, evaluated against alerts,
and broadcast to WebSocket clients as a `TICK` message.

The original architecture diagrams mention Redis Streams and PostgreSQL. Those
are design targets/decision records, not active dependencies of this repository.

## 7. Database model

The schema defines:

- `users`
- `devices`
- `watchlists`
- `watchlist_items`
- `alerts`
- `alert_events`
- `market_snapshots`
- `technical_signals`
- `news_items`
- `notifications`
- `notification_jobs`
- `orders`
- `portfolio_holdings`

Important constraints and indexes include:

- Unique watchlist symbol per watchlist.
- Unique `(alert_id, market_event_id)` idempotency key.
- Foreign keys with cascading deletes.
- Hot-path indexes for watchlists, symbols, market time series, active alerts,
  notifications, alert events, and orders.

The application uses a fixed demo identity, `user_harish`; this is not an
authentication implementation.

## 8. Failure handling and resilience already present

- SQLite WAL and busy timeout improve concurrent read/write behavior.
- `BEGIN IMMEDIATE` serializes alert transitions and pin toggles.
- Alert state is re-checked inside the transaction.
- Unique alert-event constraint prevents duplicate logical triggers.
- WebSocket clients reconnect after disconnect.
- Health endpoint exposes market data quality/staleness.
- Provider calls have explicit fallback/status behavior.
- IndianStockAPI uses a five-minute in-memory TTL cache.
- Email delivery is decoupled from market event handling.
- Frontend can reconcile through REST after reconnect/refresh.

The implementation still has prototype limitations: some WebSocket exception
handling is intentionally permissive, reconnect backoff is timer-based rather
than a full capped exponential strategy, and there is no durable distributed
queue for retries.

## 9. Tests and verification

The backend test file is
[`backend/tests/test_backend.py`](../backend/tests/test_backend.py). It covers:

1. Database initialization and seed data.
2. Volume anomaly and attention-score calculations.
3. Concurrent alert idempotency.
4. Deterministically mocked Groww SDK quote/LTP behavior.
5. Buy/sell order persistence and invalid sell rejection.
6. Atomic watchlist pin toggling.

Run the backend tests:

```bash
./venv/bin/pytest backend/tests/test_backend.py
```

Latest verification in this workspace: **5 passed, 1 failed**. The failing order
assertion is test-state contamination: `portfolio_holdings` already contains a
previously persisted BPCL quantity while the test derives its expected value from
the mutable in-memory catalog. This should be fixed by resetting/isolating test
data and holdings between tests before treating the suite as green.

Build and lint the frontend:

```bash
cd frontend
npm run build
npm run lint
```

Run the combined demo:

```bash
./venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 --app-dir backend
```

Then open `http://localhost:8000`.

Latest frontend verification: `npm run build` passes. `npm run lint` exits
successfully but reports warnings for unused imports/variables and a few React
hook dependency/style rules.

## 10a. Local migration and required configuration

Run `docker compose up -d` to start PostgreSQL and Redis, then copy
`.env.example` to `.env`. The default local values are:

- `DATABASE_URL=postgresql://groww:groww@localhost:55432/groww_lens`
- `REDIS_URL=redis://localhost:6379/0`
- `REDIS_ENABLED=true`

In this workspace, host port `5432` was already occupied by a native PostgreSQL
server, so Docker PostgreSQL is exposed on host port `55432` and the local
`.env` has been configured accordingly. The existing native PostgreSQL service
was not stopped or modified.

The backend bootstraps the schema and existing demo seed data on startup. If either
service is unavailable, it falls back to `backend/groww_lens.db` and a local asyncio
queue so existing tests and development remain usable. External provider keys are
optional: `GROWW_API_KEY`/`GROWW_API_SECRET` (quotes and holdings),
`INDIAN_STOCK_API_KEY` (news/peers), and `RESEND_API_KEY` (email).

## 10b. Recommended next steps before production

1. Add real authentication and derive the user from a verified session/token.
2. Split market ingestion, analytics, alert evaluation, and notifications into
   independently restartable workers.
3. Add durable retry/backoff and dead-letter handling for email/provider failures.
4. Connect a real streaming market provider and persist canonical market events.
5. Add authorization checks to every user-scoped route.
6. Add API contract tests and frontend component/integration tests.
7. Replace demo news/timeline templates with provider-backed, timestamped data.
8. Add deployment configuration, metrics, tracing, secrets management, and
   operational dashboards.

## 11. Final assessment

The project has delivered the core differentiated demo promised in the plan:
an event-driven watchlist that detects meaningful changes, explains them,
triggers reliable stateful alerts, and synchronizes connected devices. The main
gap is not product breadth; it is production hardening and infrastructure:
distributed eventing, real authentication, durable workers, and real market/news
data should be the next phase.
